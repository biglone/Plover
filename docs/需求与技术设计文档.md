# Plover: 以计划为中心的 GUI 智能体系统需求与技术设计文档

## 1. 系统概述
Plover 是一个以“任务计划”为中心的视觉 GUI 自动化协同系统 [1]。其核心理念是将隐藏在大模型内部的规划过程“外化”为持久、可视、可编辑的工件（Artifacts），从而支持人类与智能体的协同纠错，打破传统智能体出错后必须“推倒重来”的局限 [1-3]。

**核心设计原则 (Design Goals)：**
*   **状态不变性 (State Invariant)：** 已经执行的历史步骤绝对不可修改，所有重规划只能针对待处理步骤进行局部修复 [4]。
*   **系统状态可见性 (Execution Legibility)：** 提供类似 Git 风格的计划分支时间线，使得任务的演变完全可追溯 [3, 5]。
*   **多模态局部纠错 (Grounded Local Repair)：** 允许用户直接在实时屏幕截图上画框，以空间坐标作为修复原语 [6, 7]。

---

## 2. 技术栈选型
根据系统跨平台架构的要求，技术选型如下 [8, 9]：
*   **大语言模型 (LLM)：** 强制使用具备原生计算机控制能力的视觉大模型，采用 可以先使用 Codex cli 支持的模型。
*   **前端交互界面 (Agentic Interface)：** React + TailwindCSS [8]。
    *   *关键组件：* HTML5 Canvas（用于覆盖在 VNC 画面上实现画笔、画框等多模态标注）[8]。
*   **后端规划器服务 (Planner Service)：** Python 3.10 + FastAPI，提供 RESTful API 与前端通信 [8]。
*   **后端执行器服务 (Executor Service)：** Python 3.10，通过 gRPC 与 Planner 进行通信 [9]。
*   **运行环境与底层驱动 (Execution Environments)：**
    *   Ubuntu 环境 (Docker化)：使用 `xdotool` 执行键盘鼠标动作 [9]。
    *   Windows 环境：使用 `pyautogui` 执行动作 [9]。
    *   画面推流：采用 VNC 协议，将环境画面以 **1024 × 768 的固定分辨率**实时推流到前端 UI [8]。

---

## 3. 核心系统架构 (System Architecture)
系统必须严格划分为三个协同组件，实现“高层规划”与“底层执行”的彻底解耦 [10, 11]：

### 3.1 Agentic Interface (前端界面)
*   **对话与规划区 (Planner Chat & Steps Panel)：** 接收用户自然语言输入，展示由大模型生成的步骤列表。包含“批准 (Approve)”、“重新生成 (Regenerate)”按钮 [12, 13]。
*   **执行监控区 (Live View & Execution Panel)：**
    *   显示 VNC 实时画面，支持鼠标在此区域划定边界框 (Bounding Box) [7, 13]。
    *   **渐进式披露 (Progressive Disclosure)：** 默认情况下隐藏底层系统调用日志，仅展示现在进行时的可读动作摘要（如 "Clicking...", "Typing..."），原始日志隐藏在“详细日志”抽屉中 [14, 15]。
*   **溯源时间线 (Run Timeline)：** 以类似 Git 树的分支图表展示任务状态（待处理、执行中、已完成、失败）和人工/系统干预产生的新版本 [5, 16]。

### 3.2 Planner Service (规划器服务)
负责维护核心状态方程 $P_t = (C_t, U_t)$，其中 $C_t$ 是已完成序列 (Completed)，$U_t$ 是待处理序列 (Pending) [4]。
*   **强约束：** 每次触发重规划时，必须在代码层面强制约束 $C_{t+1} = C_t$（即过去已执行的步骤不可变） [4]。
*   **Token 优化管理：** 保留完整的文本计划历史，但在向 LLM 传递上下文时，视觉图像**最多只保留最近的 3 张截图** [17]。

### 3.3 Executor Service (执行器服务)
接收 Planner 发出的确定性指令，将其转化为系统底层的 API 调用，并监控环境状态 [11]。
*   **统一的 gRPC 接口契约：** 必须提供标准化的原语，包括：指针操作、键盘输入、滚动、等待、截图观察 [11]。无论底层是 Ubuntu 还是 Windows，接口定义必须完全一致 [9]。

## 4. 核心算法与工作流实现

### 4.1 多模态标注触发重规划 (Multimodal Annotation Workflow)
1.  用户在 Canvas 上画框，前端计算边界框坐标集合 $b(A) = (x_{min}, y_{min}, w, h)$ [7]。
2.  前端将截图 $I_t$ 与坐标 $b(A)$ 封装，通过 REST API 发给 Planner [7, 18]。
3.  Planner 锁定 $C_t$ 历史，要求 LLM 基于新的空间约束生成局部的修改提案 (Proposal) [18, 19]。
4.  用户在前端点击“批准”后，系统覆盖原有的待处理序列，继续执行 [18]。

### 4.2 系统驱动智能重规划 (System-Driven IR / 防卡死算法)
必须在 Executor 侧实现论文 Algorithm 1 逻辑 [20]：
1.  **行为重复检测：** Executor 记录最近的动作序列。如果检测到重复行为（如“连续多次点击相同区域”），进入图像校验 [21]。
2.  **画面感知哈希对比：** 提取最近 3 张截图，计算感知哈希 `h_t = dHash(s_t)` [21]。
3.  **计算汉明距离：** 计算相邻截图哈希值的 Hamming距离。如果 $d > 40$，说明画面有实质变化，属于正常重试 [20, 21]。
4.  **触发拦截：** 如果动作重复且汉明距离极小，判定画面卡死未动，强制中止步骤并标记为 Failed [21, 22]。
5.  系统向 Planner 发送带类型的拦截消息 `<failure_detected>`，触发 LLM 生成恢复提案 [20]。

## 5. 提示词工程与安全约束 (Prompt Engineering)

在调用 LLM API 时，必须注入以下 XML 标签结构和硬性约束：

### 5.1 规划器输出结构约束 (Planner Schema)
要求 LLM 永远按以下结构返回，确保状态可被解析 [4]：
```xml
<analysis>
  <!-- 在此输出对当前屏幕和任务状态的分析 -->
</analysis>
<steps>
  <completed>
    <!-- 已执行完毕的历史步骤（LLM绝对不得修改此区域的内容） -->
  </completed>
  <pending>
    <!-- 待执行或需要修复的剩余步骤，必须是简短的、以动词开头的祈使句 -->
  </pending>
</steps>
5.2 动作标签与工具使用约束 (Action Chaining & UI Summary)
动作合并 (Action Chaining)： 提示词中强制鼓励模型将多个连续的简单操作（如一系列键盘输入）打包成一次调用，以降低延迟
。
UI 摘要协议： 在调用底层工具前，必须生成人类可读的现在进行时日志
：
<ui_summary>
  <!-- 例如: "Typing response_time into field", "Clicking on the top-left menu" -->
</ui_summary>
强制状态验证： 强制要求模型在交互前使用“渐进式缩放 (progressive zooming)”和“多次翻页 (Page-Down/Up)”确保元素可见，并在启动应用后立即截图验证
。
5.3 故障恢复提案约束 (Proposal Mode Suffix)
当防卡死算法拦截任务时，向上下文注入以下消息和后缀
：
<failure_detected type='[REPEAT_TYPE]'>
  Stuck/repetition detected. Stop. Change tactic that can solve this problem.
</failure_detected>

<PROPOSAL_MODE>
You are proposing actions only.
STRICT FORMAT:
- Output EXACTLY ONE text block containing ONLY TWO LINES:
1) SUMMARY: <one short imperative step sentence>
2) RATIONALE: <1-2 sentences explaining the detected failure and why the proposed next action helps>
- The SUMMARY must start with a strong action verb, be standalone executable, and NOT contain "I will" or tool names.
- Do NOT restate the original request.
- Then output tool_use blocks if needed. No other prose.
</PROPOSAL_MODE>
5.4 降级使用限制与安全终止 (Stopping Conditions)
降级工具： 在提示词中明确，处理复杂网络请求应优先使用 curl，解析复杂文档使用 pdftotext，以补充视觉解析的不足
。
硬性终止条件： 如果任务遇到主观歧义，或遇到需要输入密码、凭证等敏感数据时，系统必须立即停止执行，并主动在 Chat 中请求用户指导
。
